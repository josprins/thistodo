## Project Overview

**thistodo** is a simple Todo web application built with React, styled with Bootstrap (Bootswatch theme), and deployed to GitHub Pages. It was bootstrapped with Create React App.

- **Live URL**: http://josprins.github.io/thistodo
- **Language**: JavaScript (ES6+, no TypeScript)
- **Framework**: React 16 (class components)

## Application Architecture

### `src/App.js` — Main Component

The entire application lives in a single class-based React component.

**State shape:**
```js
{
  items:   [{ id: Number, text: String }],  // list of todos
  newItem: { id: Number, text: String }     // current input draft
}
```

**Key methods:**
- `handleInput()` — keeps `newItem` in sync with the text input
- `addItem()` — validates non-empty input, appends to `items`, resets draft
- `updateItem(id, text)` — replaces `text` of a specific todo by id
- `deleteItem(id)` — removes a todo by id after browser `confirm()`
- `alertMessage(type, msg)` — imperatively injects a Bootstrap alert into the DOM via `document.getElementById('alert')`

**ID generation:** `Date.now()` — suitable for a single-user client-side app.

### Styling Conventions

- Bootstrap utility classes (e.g. `btn`, `form-control`, `list-group`) come from `bootswatch.css` — **do not edit this file**.
- Custom layout rules live in `src/App.css`.
- The container is responsive: full-width below 850 px, 55 % width above.
- The add-item form uses flexbox: 80 % input, 20 % button.

### Alerts

Alerts are rendered by directly manipulating `document.getElementById('alert')` rather than through React state. This is intentional legacy behaviour — match this pattern when modifying alert logic, or refactor the entire flow consistently if changing it.

## Testing

- Test files use the `*.test.js` naming convention.
- `src/setupTests.js` extends Jest with `@testing-library/jest-dom` matchers.
- Run `npm test` for interactive watch mode, `CI=true npm test` for a single pass.
- **Note:** `App.test.js` currently contains a placeholder test; it will fail until updated to match the real rendered output.

## Deployment

The app is hosted on GitHub Pages via the `gh-pages` package.

1. `npm run build` compiles to `/build`.
2. `npm run deploy` pushes `/build` to the `gh-pages` branch on the remote, which GitHub Pages serves automatically.

No CI/CD pipeline exists; deployment is manual.

## Branch Conventions

- `master` — stable, deployed state.
- Feature branches use the pattern `<author>/<description>-<id>` (e.g. `claude/add-claude-documentation-nKKzm`).
- All development should happen on a feature branch and be merged into `master` via pull request.

## Key Constraints & Gotchas

- **No TypeScript** — keep all new files as `.js`.
- **Class components** — the existing component is class-based. New components may use hooks, but be consistent within a file.
- **No state management library** — use React component state. Do not add Redux, Zustand, etc. without discussion.
- **`bootswatch.css` is a vendored file** — do not modify it. Update it only by replacing it with a new Bootswatch release.
- **Service worker is disabled** — `serviceWorker.unregister()` is called in `index.js`. Do not enable it without testing offline behaviour.
- **No custom ESLint/Babel config** — CRA defaults apply. Do not add config files that override CRA unless intentionally ejecting.
